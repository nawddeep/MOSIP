## 3. Where the three workflows touch face capture or auth

| Workflow | Today | File(s) |
|---|---|---|
| Resident face capture | SBI capture as above. Attempts are tracked per field/modality (`incrementBioAttempt`). | `lib/ui/process_ui/widgets/biometric_scan_middle_block.dart`, `lib/ui/process_ui/widgets_mobile/biometric_capture_scan_block_portrait.dart`, `BiometricsDetailsApi.java` |
| Operator login | **Password only** (`AuthResponseApi.login(username, password, isConnected)`). There is **no face login**. `AuthMode.FACE` exists in the enum but is unused. | `lib/ui/login_page.dart`, `lib/provider/auth_provider.dart:188`, `AuthenticationApi.java` |
| Operator onboarding (face enrolment) | SBI capture with `fieldId = "operatorBiometrics"` | `lib/ui/onboard/widgets/operator_biometric_capture_scan_block_view.dart` |
| Supervisor approval | **Password only** (`PacketAuthApi.authenticate(username, password)`) inside the approve-packet dialog | `lib/ui/approve_packet/widget/authenticate_dialogbox.dart:64`, `lib/provider/auth_provider.dart:208` |

**Gap (stated per the rules, no API invented):** MOSIP Android RegClient has no face-login or face-match API. Liveness alone proves "a live person is present", not "this is operator X". Proposal (implemented in Phase 5): a liveness **gate** on top of the existing password auth for operator and supervisor, behind a new `FaceLivenessApi` channel. Face *matching* against the operator's onboarded template needs a MOSIP bio-SDK, so it is listed as future work.

## 5. Where liveness plugs in

1. **Resident**: before `BiometricsDetailsApi.invokeDiscoverSbi` for modality `Face` (and `Exception` photo excluded). The Flutter Face scan button opens the liveness screen first. Only on SUCCESS does it call `invokeDiscoverSbi`. Native side: `BiometricsDetailsApi` also refuses `Face` capture without a fresh, single-use liveness token (defence in depth, so a UI bypass cannot skip it).
2. **Operator login**: after a successful password `login()` and before navigating to home, if policy `operator.enabled`.
3. **Supervisor approval**: after a successful `authenticatePacket()` and before `submitSelected()`, if policy `supervisor.enabled`.

## 6. Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | **Binding gap**: liveness runs on the app's own CameraX session, while the stored biometric comes from the MDS. An attacker could pass liveness live, then present a photo to the MDS. | Short-lived, single-use liveness token checked natively before SBI capture (time window, default 60 s). Future work: an MDS with built-in PAD (SBI 1.0 has no liveness field), or face-match of the SBI image against the last liveness frame. |
| R2 | The MDS app and our CameraX both need the front camera. | We release the camera (`unbindAll`) before SUCCESS is emitted, and the SBI intent starts only after that. |
| R3 | Flutter 3.10 / Dart 2.19 language level | Dart code avoids Dart 3 features. |
| R4 | APK size: MediaPipe (~10 MB/ABI), ONNX Runtime (~8 MB/ABI), OpenCV (~20 MB/ABI) | ABI splits are recommended. The OpenCV dependency is isolated to one adapter class (`OpenCvQualityAnalyzer`) so it can be removed. |
| R5 | Password-only auth today means "face login" is new UX and new policy | Disabled by default for operator/supervisor in bundled config (`enabled:false`). Resident is enabled. |
| R6 | No certified L0/L1 device or attack dataset available in this environment | Mock video frame source, synthetic trace harness, honest reporting in Phase 7. |
| R7 | Model provenance: MiniFASNet weights (Minivision, Apache-2.0), ONNX conversion by a third party (Apache-2.0) | SHA-256 pinned in `models/manifest.json` and verified at load. Outputs must be re-validated against the upstream PyTorch reference before production. |
