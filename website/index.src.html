How it works

Three steps from counter to server.

Each registration follows the same order. The process definition comes from your MOSIP server, so the forms match your programme's ID schema.

01 / CaptureFig. A
Step 01

Capture

The operator records consent, the resident's details and supporting documents, then captures biometrics with certified devices.

  • Forms rendered from the server's UI specification
  • Documents scanned page by page with a reference number
  • 10 fingers, 2 irises and a face, with quality scored against thresholds
Step 02

Verify

Before the face is captured, the client checks that a live person is present. A passive check runs first. When it isn't confident, it asks for random challenges.

  • Blink, smile, turn left, turn right; 2 per attempt
  • 8 seconds per challenge, 3 attempts per session
  • A supervisor reviews and approves or rejects each packet
Step 03

Trust

The registration becomes a packet that is encrypted and signed with the machine's own key. It is synced and uploaded to the MOSIP server, which reports its processing status.

  • Login and packets signed by a registered machine
  • Upload when online, or export and carry
  • Server status tracked per Application ID
By the numbers

What a single registration involves.

These figures come from the client's default configuration and code. Your deployment can change thresholds and policies.

Biometric attributes

Liveness challenges
4

Blink, smile, turn left and turn right, drawn at random.

Seconds a pass lasts
60

A liveness pass is single use and expires after 60 seconds.

Face frames stored
0

Liveness frames stay in memory and are never written or uploaded.

Built for trust

Controls you can point to in the code.

Every claim here maps to a mechanism in the client. Where something isn't done yet, it says so below.

Frames never leave memory

Liveness frames exist only on the analysis thread. Nothing is written to disk, and logs carry timings, never images or scores.

FaceFrame · LivenessAuditRecord

Fails closed

Any engine, model or audit error ends the session as an error. There is no path to a pass without a full decision.

LivenessSession · ENGINE_ERROR

No bypass from the screen

Face capture checks a native liveness pass that the UI never sees. The pass is single use, expires in 60 s and is revoked on cancel.

LivenessGate · BiometricsDetailsApi

Machine-signed login

Every login is signed with the machine's private key. The server rejects machines an administrator hasn't registered.

SyncRestUtil.getAuthRequest · KER-SNC-155

Pinned models and config

Model files are pinned by SHA-256. Synced liveness settings need a valid integrity digest, or the last good config stays active.

manifest.json · CanonicalJson

Generic failure messages

Residents never see scores, thresholds, model names or attack types. Detail goes only to the client's audit log.

PrivacyContractTest · LivenessCopy
Not yet done
  • Not certified against ISO/IEC 30107-3. No accredited lab has tested it.
  • Attack and bona fide error rates (APCER, BPCER) are not yet measured on target devices.
  • The client checks liveness. It does not match faces 1:1; MOSIP's server handles deduplication.
Who uses it

Made for the people behind the counter.

Accounts are issued by your MOSIP administrator and tied to a registration centre and a registered machine.

REGISTRATION_OFFICER

Registration officers

Enrol new residents, update UIN details, handle lost UIN and biometric corrections.

REGISTRATION_SUPERVISOR

Supervisors

Review each packet, approve or reject it with a reason, and confirm with their password.

ADMINISTRATOR

Programme administrators

Register machines and centres, set thresholds and liveness policy through synced global parameters.

OFFLINE · FIELD

Mobile enrolment camps

Register where there's no network. Log in offline, then sync, upload or export later.
